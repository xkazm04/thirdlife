# Interest management, world layering/instancing and multiplayer authority, and implications for a single-player-first Godot sandbox

Research date: 2026-11-10. Confidence tags: [P] = primary source fetched and read; [S] = secondary (wiki, news, community); [F] = forum/low confidence; [M] = from my own background knowledge, NOT verified this session (do not cite as fact). Pages fetched via a summarizing fetch tool, so exact figures should be rechecked before they go into a design document.

## 1. Interest management / area of interest: concrete schemes and published numbers

### Takeaway
Every system answers "who needs to know about / compute what" with a spatial partition (grid, zone, node, container) plus a per-observer relevance filter, and nearly all of them put a hard bound on cost by capping or splitting the population rather than by degrading a single world. Published numeric tables (cell sizes, tier rates) are scarce in primary sources; most numbers below are about population and node capacity, not cell sizes.

### Cited Findings
- Academic baseline: Boulanger, Kienzle and Verbrugge (NETGAMES 2006) compared eight interest-management algorithms on real player data; three are plain radius-around-player, five are obstacle/visibility-aware. Obstacle-aware methods cut update messages by up to a factor of 6, and cheap tile-based methods approximated ideal visibility-based management at very low cost; their "Tile Path Distance" algorithm performed best. [P: abstract-level via search] — [paper PDF](https://www.sable.mcgill.ca/~clump/papers/boulanger-06-comparing.pdf), [dblp](https://dblp.dagstuhl.de/rec/conf/netgames/BoulangerKV06.html). The Liu and Theodoropoulos survey was not fetched (gap).
- EVE Online, nodes: a node is one EVE server process whose Python (Stackless) component is single-threaded, so it uses one CPU core. Typically many, even hundreds, of solar systems live on one node; a solar system cannot be split further, so a single system that exceeds one core cannot be balanced. A fleet-fight notification gets a system its own node (Jita is always isolated), instead of sharing with roughly 20-40 other systems. [P/S, CCP dev blogs via search snippets, 2008 to early 2020s, partly historical] — [Fixing Lag: Character Nodes](https://www.eveonline.com/news/view/fixing-lag-character-nodes), [Gridlock, Monikers, and CPU-per-user](https://www.eveonline.com/article/gridlock-monikers-and-cpu-per-user-1). Character nodes later moved services off the system node so Jita could exceed the former ~1400-pilot limit (same blog). A 2008 account: a 1200-player fight on an Intel blade after AMD nodes crashed near 700 players.
- EVE, time dilation (TiDi): the server runs tasklets on a cooperative round-robin scheduler; under overload tasklets wait seconds. Time dilation slows the game clock so the tasklet queue stays near zero; clock-tied load (modules, physics, warp) drops proportionally. A slight overload may mean ~98% time. Reinforcement timers do not dilate (so players cannot game them); shield recharge does. The article gives illustrative figures only (about 5% on warp-in, 30% once joined, 60% at ~1,200 engaged, 10% on retreat; ~1,600 ships in the example; Destiny physics only 5-10% of load; modules yield after 100 ms). It explicitly says a minimum rate is needed but does not fix one, and the text I read is the original proposal (a prototype, not shipped), so the shipped TiDi minimum (commonly cited as 10%) is [M] and unverified here. — [Introducing Time Dilation](https://www.eveonline.com/news/view/introducing-time-dilation-tidi)
- Unreal Replication Graph: groups actors by location, suggests grid spaces for battle royale/MOBA/MMO or predefined rooms/zones; lists "always relevant" nodes (global, or per player/team), dormant lists for pre-placed actors (example: a tree dormant until damaged), carried items replicate only with their owner; replication lists are built per client connection. Fortnite Battle Royale: 100 connections and about 50,000 replicated actors at game start. No cell size or default values are given on the page. Disabled on consoles (splitscreen). — [Replication Graph docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/replication-graph-in-unreal-engine) [P]
- Unreal classic relevancy: NetCullDistanceSquared is the squared distance cutoff from the client viewpoint; NetUpdateFrequency is the max and MinNetUpdateFrequency the min rate; dormancy can be per-client via DormantPartial plus GetNetDormancy override; the server checks relevancy, update frequency and dormancy when gathering actors. Found mostly via forum threads and legacy UE3/UE4 docs [F/S] — [UE 4.27 replication performance doc (URL returned 403 to fetch; cited via search)](https://docs.unrealengine.com/4.27/InteractiveExperiences/Networking/Actors/ReplicationPerformance), [UDN relevancy page](https://udn.epicgames.com/Three/ReplicationRelevancy.html).
- Unreal Significance Manager: a central framework that scores registered objects against viewer transforms (highest score wins, or lowest if ascending), then calls post-significance callbacks (concurrent or sequential most-to-least significant). It does not improve performance by itself; the project defines scoring and the response (disable emitters, run AI less often). The page publishes NO tier table or thresholds. — [Significance Manager docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/significance-manager-in-unreal-engine) [P]
- Improbable SpatialOS (historical; Improbable wound down the SpatialOS game offering around 2022 [M], not verified here): query-based interest (QBI) replaced the earlier fixed chunk/grid checkout; constraints include sphere, cylinder, box and relative-to-entity variants; a worker authoritative over a component receives updates for entities matching that component's interest queries; queries can carry a maximum update frequency, and a patent describes a large radius at low rate combined with a small radius at high rate. "Checkout radius" as a term was not found in the sources. — [Improbable engineering blog](https://medium.com/improbable-engineering/thinking-spatially-using-dynamic-interest-management-to-create-revolutionary-game-designs-80ed0fe7693), [patent US10579434](https://patents.google.com/patent/US10579434), [schema listing](https://rust-digger.code-maven.com/src/spatialos-codegen-0.2.2/examples/schema/standard_library/improbable/standard_library.schema) [S/P-patent]
- Star Citizen: client OCS (object container streaming) shipped 2018, server OCS end of 2019 (servers unload containers with no players nearby). Authority model: one server node holds authority over an entity, other nodes hold client views; at the time of the Q&A authority transferred only between client and a single server. Persistent Streaming stores all replicated entity state in a graph DB (EntityGraph). Static mesh = fixed server nodes per shard and fixed location assignments, limited scaling; dynamic mesh = continuous rebalancing and authority transfer with a Fleet Manager. Shards held about 50 players at that time; long-term goal 100 players seeing each other. Q&A was a forward-looking plan (2021 timing), so shipped status as of Nov 2026 is NOT verified. A wiki states an 800-player meshing test in March 2024 [S]. — [CitizenCon Q&A comm-link 18397](https://api.star-citizen.wiki/comm-links/18397) [S: fan-hosted copy of official comm-link], [Star Citizen wiki OCS](https://starcitizen.tools/Object_Container_Streaming) [S]
- Guild Wars 2 megaserver: a weighted load balancer scoring each map copy by party, guild, language, home world and friends; copies are added as needed so there is no overflow; region (NA/EU) still separates players. Prototype results: average population per map copy +225%, players on same map as party +25%. Rolled out April 2014. Large guilds later complained about difficulty getting everyone into one instance; ArenaNet added reservation features and a map queue beta (2023). — [ArenaNet announcement](https://www.guildwars2.com/en/news/introducing-the-megaserver-system/) [P], [PC Gamer coverage](https://www.pcgamer.com/guild-wars-2-moving-to-megaserver-system-arenanet-aim-to-populate-quieter-zones) [S]
- WoW sharding/layering/phasing: no primary Blizzard blue post with mechanics was found; summaries say layering is Classic-specific, a player's layer persists across zone changes unlike retail sharding, and a Blizzard engineer said Classic content (e.g. Rexxar's long patrol path) is not designed for sharding. Phasing is described as per-player (quest-progress) world-state variants, not a capacity tool. [F/S] — [Wowhead summary](https://www.wowhead.com/news=294589/blizzard-clears-up-layering-tech-misconceptions-in-classic-wow), [Blizzard forum threads](https://us.forums.blizzard.com/en/wow/t/how-does-phasinglayering-work/746910). Treat all as lower confidence.
- Minecraft: hosting-provider docs describe view distance (radius of chunks sent to clients) and simulation distance (radius of chunks actually ticked: crops, mobs, redstone) as separate settings; ranges quoted conflict (e.g. 3-32 vs 1-32 vs 4-32); default 10 reported. Entity tracking ranges were not found. [S, hosting vendors] — [Shockbyte](https://shockbyte.com/help/knowledgebase/articles/changing-view-and-simulation-distances-on-a-minecraft-server). The view-distance versus simulation-distance split itself is the useful pattern.

### Inferences
- The strongest common pattern is a split between "what is loaded/visible" and "what is simulated" (Minecraft view vs simulation distance, Star Citizen client vs server OCS, Unreal dormancy). That maps directly to the owner's rule that every game stays alive: alive means state is retained and evolvable, not that it ticks at full rate.
- Capacity is bought mainly by partitioning to a unit that cannot be split further (EVE: solar system on a core; SC: container/server). In a single-process Godot game the analogous unit is "a pack's venue", with its Jolt bodies, as the atom of simulation cost.
- Radius-based interest is cheap and good enough; obstacle-aware variants (Boulanger) only pay off when occlusion is strong, which is not a concern for a landscape of discrete venues.

### Gaps
- Cell sizes, view distances and tier tables: none found published for EVE, WoW, GW2, Minecraft or Replication Graph defaults. Epic's own default grid cell size (I recall 10,000 uu in the ShooterGame/Fortnite-derived example) is [M], unverified.
- Unreal Iris (filtering, prioritization, NetObjectFilter, dynamic filters) not fetched.
- Liu and Theodoropoulos survey not fetched. EVE "brain in a box"/node-per-system details beyond the blogs above not found; the shipped TiDi floor not verified.
- Minecraft entity tracking ranges and mob-cap/despawn distances not verified.

## 2. Layering and instancing: how rules are scoped to a region, boundary crossing, fit for "a pack owns a plot"

### Takeaway
Patterns divide into (a) copies of the same space for capacity (GW2 megaserver, WoW sharding/layering, SC shards), (b) per-observer variants of one space (WoW phasing), and (c) region-owned authority (SpatialOS workers, SC server meshing, EVE system-per-node). Primary sources say little about rules scoped to a region (battlegrounds, minigames); that part is mostly my design inference, flagged below.

### Cited Findings
- GW2 copies are interchangeable capacity layers chosen by a scoring function, with party/guild joining as an override. [P] — [ArenaNet](https://www.guildwars2.com/en/news/introducing-the-megaserver-system/)
- WoW layering persists per player across zone boundaries, and Blizzard states content must be designed to tolerate it (Rexxar example). [S/F] — [Wowhead](https://www.wowhead.com/news=294589/blizzard-clears-up-layering-tech-misconceptions-in-classic-wow)
- SC: entity authority belongs to exactly one server node; other nodes see replicas; authority transfers when an entity crosses node regions (in plan). [S] — [comm-link 18397](https://api.star-citizen.wiki/comm-links/18397)
- SpatialOS: authority is per component per worker, and a worker's interest is derived from queries, which means a boundary crossing is an authority and interest handover rather than a state copy. [S/P-patent] — [US10579434](https://patents.google.com/patent/US10579434)
- Unreal: always-relevant and per-team lists let one object belong to a special replication set temporarily (a reveal power, then returns to the default node). [P] — [Replication Graph](https://dev.epicgames.com/documentation/en-us/unreal-engine/replication-graph-in-unreal-engine)

### Inferences (design-level, not sourced facts)
- Fit for "pack owns a plot with local rules": a region-owned rule scope (the SpatialOS/SC "one authority owns a region" shape, scaled down to one authority per venue). Rules attach to the plot, and an entity entering it is governed by the plot's rule set only while inside; crossing is an explicit handover event (rule-set swap, input remapping, tag change) rather than the entity carrying rules.
- Fit: WoW phasing generalized as "per-participant view of world state" is the right primitive for later multiplayer (same venue, different players' progress) but is a misfit now as a rule-scoping device; it hides state per observer, which complicates determinism.
- Partial fit: instancing/copies (GW2, layering). Useful later: the same pack can be instantiated per player group as an isolated sim with its own seed and input stream. Misfit as a cost tool now, because the owner requires one continuous landscape.
- Misfit now: dynamic server meshing and EVE-style node balancing; these solve multi-machine scaling, which does not exist in single-player.
- Boundary hazards: entity straddling two plots (physics body overlapping two rule scopes) should be forbidden by construction, e.g. buffer margins, or the entity is owned by the plot containing its origin at tick start.

### Gaps
- No primary source found on rule scoping for battlegrounds/minigames (WoW battleground instancing, EVE faction warfare plexes, Fortnite/UEFN islands). Not researched deeply.
- Entity-crossing semantics for SC/SpatialOS beyond the above not verified.

## 3. Update-rate tiers by relevance

### Takeaway
The mechanisms exist (min/max update frequency, dormancy, query max-frequency, significance scoring, TiDi), but published tier tables do not. The only concrete published numbers are Gaffer's snapshot rates and EVE's illustrative dilation figures.

### Cited Findings
- Unreal: NetUpdateFrequency (max) and MinNetUpdateFrequency (min) bound a per-actor rate scaled by priority/relevance; dormancy suspends replication until a flush. [F/S] — [UE 4.27 doc via search](https://docs.unrealengine.com/4.27/InteractiveExperiences/Networking/Actors/ReplicationPerformance)
- Unreal Significance Manager supplies the score but no tiers; the game decides (AI tick rate, particles). [P] — [docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/significance-manager-in-unreal-engine)
- SpatialOS queries accept a max update frequency; patent describes near-high-rate, far-low-rate pairs. [S] — [US10579434](https://patents.google.com/patent/US10579434)
- Gaffer On Games: 60 snapshots/s at ~25 KB each is ~11.6 Mbit/s; 10/s is ~6x less (~2 Mbit/s). Interpolation buffer ~3x send interval: 300 ms at 10 Hz, about 150 ms at 30 Hz, about 85 ms at 60 Hz. — [Snapshot Interpolation](https://gafferongames.com/post/snapshot_interpolation/) [P]
- EVE TiDi is a global slowdown of the whole node's clock rather than per-entity LOD. — [CCP](https://www.eveonline.com/news/view/introducing-time-dilation-tidi)

### Inferences
- For a deterministic fixed-tick sim, per-entity variable rate is dangerous unless the tier decision is itself a deterministic function of sim state. The safe form: "tier changes are derived from recorded state or from the input record", never from wall-clock, frame time or camera.
- Three distinct options, in descending determinism-safety: (1) same tick rate, less work per tick (coarser AI, sleeping bodies); (2) fixed sub-rate (a pack ticks every Nth fixed tick, N a pure function of distance bucket with hysteresis); (3) analytical fast-forward on re-entry (advance a coarse model by elapsed ticks). Option 3 is a "catch-up" scheme and must also be deterministic and tick-count based.
- EVE-style global time dilation is an available last-resort valve for a lockstep sim (slow the whole world clock when over budget), and keeps determinism intact because tick count, not wall time, drives the sim.

### Gaps
- No published numeric tiers (e.g. 60/30/10 Hz by distance) were found in primary sources for any system listed. Any such table would be [M].

## 4. Multiplayer implications for a single-player-first deterministic 60 Hz design

### Takeaway
A deterministic fixed-tick sim with a complete per-tick input record is the single most valuable multiplayer-ready property (lockstep or rollback become possible, replays/desync checks come free), but it is also the most fragile: determinism is only guaranteed for the same binary and same call order, and Jolt cross-platform determinism needs a specific build. Godot's built-in Jolt integration documents no determinism guarantee.

### Cited Findings
- Jolt determinism conditions (official docs): API calls that modify the simulation must occur in identical order (bodies and constraints added/removed/modified in the same sequence); the same binary must run the simulation (CPU vendor does not matter on the same binary). — [Jolt docs, Deterministic Simulation](https://jrouwe.github.io/JoltPhysics/#deterministic-simulation) [P]
- Cross-platform: enable CMake `CROSS_PLATFORM_DETERMINISTIC` (about 8% slower); intended to be deterministic regardless of compiler, configuration (Debug/Release/Distribution), OS, architecture, 32/64-bit. Tested: MSVC 2022, clang, gcc, emscripten; Windows, macOS, Linux; x86, ARM, RISC-V, PowerPC, LoongArch. Docs say it is less tested than other features. Same source and same defines everywhere (e.g. not mixing JPH_DOUBLE_PRECISION). [P] — same page.
- Floating-point requirements: precise mode (`/fp:precise`, `-ffp-model=precise`), `-ffp-contract=off`, consistent FPU state (round-to-nearest, DAZ/FTZ consistent across threads). [P] — same page.
- Non-deterministic surfaces in Jolt: broad-phase queries (use custom CollisionCollector and sort), narrow-phase query result order, all listener callbacks (contact, activation, step; multithreaded, so order varies), `GetActiveBodies` order. Constraint order matters unless each has a unique `mConstraintPriority`; `SaveState` depends on constraint ordering. Use Jolt's Sin/Cos/QuickSort/Hash rather than std versions inside simulation code. [P] — same page. Jolt provides a "Check Determinism" mode (StateRecorder, rewind, rerun the step and compare). [P]
- Godot's built-in Jolt docs: say nothing on determinism; the module is described as thread-safe but experimental when multithreaded. [P] — [Godot: Using Jolt Physics](https://docs.godotengine.org/en/latest/tutorials/physics/using_jolt_physics.html). The earlier godot-jolt extension docs stated that Jolt is deterministic but that the extension could not guarantee it, and that apparent determinism should not be relied on. [S, via search snippet] — [godot-jolt](https://github.com/godot-jolt/godot-jolt). Godot builds Jolt itself, so whether Godot's build flags set CROSS_PLATFORM_DETERMINISTIC and fp-contract settings was NOT verified (gap). A forum user's claim that Rapier offers cross-platform determinism is [F].
- Gaffer On Games on lockstep: identical initial state plus identical inputs give bit-identical results; same delta time required; determinism on one machine/binary/OS does not carry across compilers, OSes or architectures; debug vs release may differ; "there's no silver bullet". Bandwidth scales with input size, not object count (a million-object sim can use the same bandwidth as one object). Input delay buffer (his demo used 100 ms); input stall if input n is missing; send all unacked inputs redundantly over UDP; cap at 4 sim steps per render frame to avoid spiral of death. — [Deterministic Lockstep](https://gafferongames.com/post/deterministic_lockstep/) [P]
- Gaffer on snapshot interpolation: the receiver runs no simulation; lockstep is recommended only for small player counts (2-4) because everyone waits on the most-lagged player and FP determinism is hard. — [Snapshot Interpolation](https://gafferongames.com/post/snapshot_interpolation/) [P]
- Authority model for large worlds in production is server-authoritative replication with interest management (Unreal Replication Graph for Fortnite's ~100 players/50,000 actors; SC one-authority-per-entity; SpatialOS authority per component). Lockstep/rollback is absent from MMO-scale designs, which is consistent with Gaffer's 2-4 player guidance. [P/S]

### Inferences
- Which model tolerates user-authored scripted games: 
  - Lockstep or rollback: tolerates scripts only if scripts are pure functions of (sim state, input stream, a seeded sim RNG) and run on every peer. It is a good fit for small groups (2-8) sharing a pack such as hockey or racing, and a partial fit for a shared persistent world (everyone must simulate everything they interact with; one slow peer stalls; late joiners need a snapshot).
  - Server-authoritative state replication: the scripts run only on the server; clients get state. Tolerates arbitrary scripts (non-deterministic code is fine) but needs a replicable state schema per pack and cannot reuse the single-player sim unchanged. Best fit for a big shared landscape.
  - Practical hybrid: one authoritative host runs the exact same deterministic sim as single-player (the "listen server"), clients send inputs and receive snapshots or periodic state, with client prediction/rollback only inside active mini-games. The single-player build then already is the server.
- What the deterministic 60 Hz fixed tick with per-frame input records buys now: replay, regression tests, desync detection (hash of state per N ticks), save games as (snapshot, input log), headless server mode, and a later choice between lockstep and authoritative server.
- Decisions expensive to reverse (derived from the sources above plus standard practice):
  1. Input read outside the input stream: any script or game code that polls Input directly, or reads mouse/camera state, breaks replay and netcode. Route everything through one per-tick input record keyed by player id.
  2. Global mutable state and singletons (autoloads holding game state, static vars): block running two instances of a pack or two players; scope state per pack/world instance.
  3. Hidden randomness: global randf/randi, time-based seeds, hash-order iteration of dictionaries, node-tree order, `Time.get_ticks`, delta-dependent logic. Use a seeded per-pack RNG stored in sim state and advanced only by sim tick.
  4. Frame-rate-dependent logic outside the tick (using `_process` delta for state); keep all state changes inside the fixed step; only visuals interpolate.
  5. Jolt call order and body creation order (docs state this explicitly), unique constraint priorities, no reliance on contact-listener order or `GetActiveBodies` order; sort before acting.
  6. Floating-point and binary identity: if cross-machine lockstep is ever wanted, all peers need the same binary (or a CROSS_PLATFORM_DETERMINISTIC Jolt plus compiler flags) and the same GDScript/engine version. Floats in GDScript are 64-bit doubles on the interpreter while Jolt is single precision [M, unverified]; be explicit about quantization at boundaries.
  7. Stable entity IDs (not object instance ids or node paths), and serializable sim state: a full state snapshot and restore is a prerequisite for late join, rollback and the "layer re-entry" scheme in section 3.
  8. Authority/ownership field on every entity and every pack from day one, even if always "local".
- Lockstep scale check: Gaffer's own recommendation limits lockstep to a few players, so a shared "everyone sees everything" world should not be planned as lockstep.

### Gaps
- Not verified: whether Godot 4.x's bundled Jolt is compiled with CROSS_PLATFORM_DETERMINISTIC, FP contraction off, or whether Godot's own PhysicsServer3D ordering (e.g. body iteration, `_physics_process` order, Area/contact signals) is stable between runs. This needs a direct test (run the same input log twice, in release export and in editor, compare state hashes) and a read of Godot's `modules/jolt_physics` build config.
- Godot high-level multiplayer docs (MultiplayerSynchronizer, MultiplayerSpawner, visibility filters) not fetched; Godot has per-peer visibility on synchronizers [M], not verified.
- Gaffer's "State Synchronization" and "Networked Physics" articles and rollback (GGPO) sources not fetched.
- UE Iris and Epic's Mover/Network Prediction not covered.

## 5. Technique fit summary for the stated single-player sandbox

| Technique | Verdict | Reason |
|---|---|---|
| Grid/zone interest with per-observer relevance (Replication Graph style) | Partial fit now, fit later | Single player has one observer; the cell/venue partition is useful for tiering cost; per-connection lists matter only with multiplayer |
| Min/max update frequency, significance scoring | Fit as a pattern, with deterministic tiering | Drive tier from sim state or tick count, never wall-clock or camera |
| Dormancy/sleep with flush on change | Fit | Matches "alive but cheap"; wake on interaction or scheduled events; Jolt body sleeping already exists |
| Separate view vs simulation distance (Minecraft) | Fit | Direct analog for render LOD vs sim tier; owner rule satisfied because nothing is switched off |
| EVE time dilation | Partial fit (emergency valve) | Slows tick pace under load; keeps determinism if driven by tick count |
| EVE one-system-per-node / SC server meshing / SpatialOS workers | Misfit now | Solve multi-machine scaling; instructive for the "one authority per region" model later |
| GW2 megaserver / WoW layers (copies) | Misfit now, fit later | Capacity copies; later useful to instantiate a pack per group |
| WoW phasing (per-observer world variants) | Partial fit | Good for later per-player progression views; risky for determinism |
| SC object container streaming (stream containers in/out by proximity, persist state) | Fit | Close to "pack venue as a container whose state persists while unloaded or coarse" |
| Deterministic lockstep | Partial fit | Excellent for small-group mini-games and for the single-player replay/test benefits; poor for a large shared world (Gaffer: 2-4 players) |
| Server-authoritative snapshot replication with interest management | Fit for shared world later | Tolerates arbitrary scripts; costs a replicable state schema; the single-player build can become the host |
| Rollback | Partial fit | Needs fast snapshot/restore of Jolt state; Jolt has StateRecorder SaveState/RestoreState, but constraint-order caveats apply |
